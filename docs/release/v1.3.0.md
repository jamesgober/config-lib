# config-lib v1.3.0: strict parsing

**v1.3.0 is a security release.** TOML no longer runs NOML's `include` and `env()`, a new strict entry point refuses them in NOML as well, and the CONF, INI and Properties parsers handle non-ASCII text without panicking, hanging or going quadratic. The default feature set is unchanged and stays on Rust 1.75.

## What is config-lib?

A multi-format configuration library for Rust. One API for TOML, JSON, INI, XML, HCL, NOML, Java Properties, and CONF, with hot reload, environment variable overrides, schema validation, audit logging, and lock-free cached reads.

## Security fixes

### TOML resolved NOML `include` and `env()` (high)

The `toml` feature reads TOML through the noml crate. noml parses TOML and NOML into the same syntax tree, and config-lib resolved that tree with noml's resolver, which honours two things TOML does not have:

- `include "path"` opens any file, relative to the process's working directory, with no checks.
- `env("NAME")` copies any environment variable into a value.

A program that checks its configuration file before reading it (owner, mode, size, refusing a FIFO) had every one of those checks bypassed: the included file got no check and no size cap, and an included FIFO blocked the reader.

TOML is now checked before it is resolved. `include`, `env()` and any other function call, `@type(...)` native types and bare `${...}` are refused with `Error::Parse` and the line and column of the first one:

```text
Parse error at line 2, column 10: include is not allowed in TOML
```

The message never quotes the path or the variable name. This applies to every TOML entry point (`Config::from_string`, `from_file`, `parse`, hot reload, `parsers::toml_parser::parse` and `parse_with_preservation`) and cannot be turned off, because none of this is TOML. Keys named `include` or `env` still work, and `${...}` inside a string stays literal, as since 1.1.0.

### CONF, INI and Properties mixed character and byte positions (medium)

The three hand-written parsers counted their position in characters (`chars().nth(pos)`) and sliced the input with it as a byte offset. With non-ASCII text:

- CONF panicked: `"#ééé\n[a]\nk = 1\n"` sliced inside a character. Other non-ASCII text before a section header made valid files fail to parse.
- INI looped forever on any non-ASCII character.
- Properties refused valid files.

Counting from the start for every character also made each parse quadratic: 40 KB of CONF took about 250 ms.

The parsers now keep a byte offset that only moves by whole characters and slice with checked `str::get`. Any `&str` parses or returns an error without a panic, in linear time: 1 MiB of CONF parses in about 24 ms in a release build and well under a second in a debug build (tested). Line and column numbers still count characters from 1.

Found while testing these parsers, and fixed:

- **CONF arrays overflowed the stack** on deep nesting (a long run of `[`), which aborts the process. Nesting beyond 128 levels is now a parse error.
- **INI looped forever on a line starting with `=` or `:`.** It is now a parse error.

## Strict NOML

```rust
use config_lib::Config;

let config = Config::from_string_strict(&text, Some("noml"))?;
```

`Config::from_string_strict` takes the same arguments as `Config::from_string`, so a caller that already passes a format string switches with one edit. For NOML it refuses `include` and every function call, `env()` included, with `Error::Parse` and a position, before anything is resolved. Native types (`@size("10MB")`, `@duration("30s")`) and `${...}` references to other values in the same document still work, because they read only the document. For TOML, JSON, CONF and the rest it returns what `from_string` returns.

The same check is available as `config_lib::parse_strict`, `parsers::parse_string_strict` and `parsers::noml_parser::parse_strict`. Without a format hint, a document that uses `include` or `env(` is detected as NOML and refused.

Default NOML is unchanged: `from_string`, `from_file` and `parse` still resolve `include` and `env()`.

Cost: one pass over the syntax tree before resolving, with an explicit stack. On a 4 KiB NOML document it measured about 12 µs on top of a 340 µs parse (release build, one desktop machine; an estimate for other hardware). The CONF parser got faster on every input; 1 KiB parses in about 17 µs.

## Other changes

- **INI: an empty value no longer takes the next line.** `a=` followed by `b=2` gave `a = "b=2"`; it now gives `a = ""` and `b = 2`. A key and its separator must be on the same line.
- **INI line numbers** count a CRLF line end once.

## Breaking changes

**None in the API.** Two behaviour changes can turn a file that loaded in 1.2.0 into an error:

- A TOML file that used `include`, `env()`, a native type or a bare `${...}`. These were never TOML; move such a file to `.noml` if you rely on them.
- An INI file with a key and its `=` on different lines, or a line starting with `=` or `:`.

## Stability contract changes

`docs/STABILITY-1.0.md` gains §4.5: TOML refuses NOML-only syntax for the rest of v1.x, the strict entry points read only the text they are given, refusal messages never quote the input, and default NOML keeps resolving `include` and `env()`.

## Installation

```toml
[dependencies]
config-lib = "1.3"

# TOML and NOML (Rust 1.82+)
config-lib = { version = "1.3", features = ["toml", "noml"] }

# With everything
config-lib = { version = "1.3", features = ["jsonx", "json", "xml", "hcl", "noml", "toml", "validation", "async", "chrono"] }

# Slimmest possible
config-lib = { version = "1.3", default-features = false, features = ["conf"] }
```
