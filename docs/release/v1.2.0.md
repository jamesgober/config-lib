# config-lib v1.2.0: JSON on jsonx-lib

**v1.2.0 adds the `jsonx` feature, a second backend for the `json` format built on [`jsonx-lib`](https://crates.io/crates/jsonx-lib).** jsonx-lib has no dependencies and no unsafe code, follows RFC 8259 strictly, and refuses duplicate keys. The `json` feature and its serde_json backend are unchanged, so no 1.x user has to change anything. The default feature set is unchanged and stays on Rust 1.75.

## What is config-lib?

A multi-format configuration library for Rust. One API for TOML, JSON, INI, XML, HCL, NOML, Java Properties, and CONF, with hot reload, environment variable overrides, schema validation, audit logging, and lock-free cached reads.

## What's new in 1.2.0

### The `jsonx` feature

```toml
config-lib = { version = "1.2", features = ["jsonx"] }
```

Everything that reads or writes the `json` format works with either feature:

- `parsers::json_parser::parse` and `serialize`
- `Config::from_string`, `from_file`, `serialize`, `save` and `save_to_file`, and format detection from `.json` and from a leading `{` or `[`
- `EnterpriseConfig` load and save
- environment override values that look like JSON (`APP_DB_POOL='{"max": 32}'`)

With both features on, `jsonx` reads and writes JSON, and `json` still provides `from_json_value` and `to_json_value`, which take and return serde_json types. No public signature depends on which features are on.

### Same results as serde_json, except duplicate keys

The two backends give the same `Value` for the same document and write the same text for the same `Value`. Parity tests check this with both features on, over objects, arrays, scalars at the top level, escapes and unicode, and numbers at the edges (`i64::MIN` and `i64::MAX`, integers beyond `u64`, `-0`, subnormals, `1e-400`), plus several hundred floats across the whole exponent range.

- An integer that fits `i64` is `Value::Integer`. Any other number (a fraction, an exponent, an integer beyond `i64`, and `-0`) is `Value::Float`, as serde_json reads it. A number too large for `f64` is a parse error.
- Writing uses the pretty layout with members in key order. Floats are the shortest text that reads back as the same `f64`, with a signed positive exponent (`1e+16`) as serde_json 1.0.149 and later write it. NaN and the infinities are refused with the same errors as before. A `DateTime` is written as its RFC 3339 string.

**The one behaviour difference: duplicate keys.** `{"user": "guest", "user": "admin"}` is a parse error with `jsonx`. serde_json keeps the last value. A reader that silently picks one of two values lets a second value hide behind the first, so `jsonx` fails closed. Keys are compared after unescaping.

The `jsonx` writer also escapes U+2028 and U+2029 inside strings, which serde_json writes raw; both read back as the same string.

### Budgets and errors

With `jsonx`, jsonx-lib's default budgets apply: nesting depth 128, input 64 MiB, one string or key 16 MiB, one number 1 KiB, 1 Mi values, and 64 MiB for the parsed tree. Each is checked before the memory it guards is allocated. Nothing on the path recurses on nesting depth: jsonx-lib parses with an explicit stack, and config-lib converts the tree and writes JSON the same way. A million levels of `[` is a parse error on a 256 KiB stack.

A parse error is `Error::Parse` with the line and column (from 1) of the mistake:

```text
Parse error at line 2, column 2: JSON parse error: duplicate object key at byte 19
```

The message names the kind of mistake and its byte offset. It never quotes the input, because configuration values can be secrets.

### Fixed: the polling watcher

Hot reload without the `hot-reload` feature polls the file. It compared only modification times, so a file read while it was being written (truncated, then filled) could stay half-read: when the rest of the write landed within the file system's time resolution, nothing looked newer. It now compares the size as well.

## MSRV

| Features                 | MSRV |
|--------------------------|------|
| default and most opt-ins | 1.75 |
| `xml`                    | 1.79 |
| `noml`, `toml`           | 1.82 |
| `jsonx`                  | 1.85 |

`jsonx-lib` 0.5.1 declares `rust-version = "1.85"` (edition 2024). Having it in `Cargo.lock` does not affect builds without the feature: `cargo +1.75 build` and `cargo +1.75 test` with the default features still work. CI checks each row on exactly that version.

`jsonx-lib` is pre-1.0, so it is pinned exactly (`=0.5.1`), as `noml` is. A newer jsonx-lib reaches users only through a config-lib release. See `docs/STABILITY-1.0.md` §4.4.

## Breaking changes

**None.** `jsonx` is a new, opt-in feature. With `json` alone, behaviour is the same as in 1.1.0.

## Installation

```toml
[dependencies]
config-lib = "1.2"

# JSON on jsonx-lib (Rust 1.85+)
config-lib = { version = "1.2", features = ["jsonx"] }

# With everything
config-lib = { version = "1.2", features = ["jsonx", "json", "xml", "hcl", "noml", "toml", "validation", "async", "chrono"] }

# Slimmest possible
config-lib = { version = "1.2", default-features = false, features = ["conf"] }
```
